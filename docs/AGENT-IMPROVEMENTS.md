## 1. P0 — сделано в этом заходе

### 1.1. История прогонов и аудит-след (FACT: внедрено)

**Проблема (FACT).** У каждого запуска обработчика был свой файл `/var/lib/hermes-agents/logs/*.log`,
но их никто не сводил. На вопрос «падал ли этот агент вообще?» ответа не существовало: 39 файлов
журналов на узле — это не статистика. Агент, который ломается на каждом запуске, выглядел ровно так же,
как работающий: ни метрики, ни алерта.

**Что сделано.**
- `agents/runtime.py` — один JSON-строкой на прогон в `/var/lib/hermes-agents/history.jsonl`:
  агент, обработчик, кто попросил (`actor`), код возврата, длительность, путь журнала, первая строка вывода.
  Файл только дописывается, режется по 5 МБ (`history.jsonl.1…3`), что печатал владелец — не пишется
  (`HISTORY_SKIP_ARGS`: message/text/prompt/token/password). Запись не может уронить работу: исключение
  логируется и проглатывается.
- `agents/checks/history.sh` — человеческий отчёт: прогонов/ошибок/p50/p95 по каждому агенту, последние
  ошибки с кодом возврата, ссылка на журнал и на сам файл истории.
- `scripts/hermes_metrics_exporter.py` — `probe_agent_history()`: `hermes_agent_runs_total`,
  `hermes_agent_failures_1h`, `hermes_agent_duration_p95_ms`, `hermes_agent_last_run_timestamp_seconds`.
- `deploy/monitoring/hermes-agents.rules.yml` — правило `HermesAgentFailing`: ≥3 упавших прогонов за час →
  предупреждение владельцу.

**Зачем это владельцу.** Появился ответ на два вопроса, которых раньше не было: «что агенты делали» и
«что из этого не получилось». Заодно это audit trail для действий: «перезапусти octopus-browser» оставляет
запись «кто попросил, что вышло» — не только текст в чате.

**Как проверить.** `bash agents/checks/history.sh`; в Telegram — «что делали агенты».

### 1.2. Конвенция доказательств (FACT: внедрено)

**Проблема (FACT).** Только 1 из 27 проверок упоминал источник своих утверждений. Инцидент 2026-09-17
показал цену: 14 агентов печатали «дерево чистое / всё отправлено», не прочитав ни байта.

**Что сделано.** В `lib/report.sh` добавлены `report_proof "<команда>"` (строка «↳ доказательство: …»
под утверждением) и `report_unknown "<что не удалось>"` (отказ посмотреть — полноценный ответ).
`project-check.sh` уже печатает под git-вердиктами команды, которыми они получены.

**Следующий шаг (P1, дёшево).** Пройти по 27 проверкам и добавить `report_proof` там, где есть числа и
вердикты: `guardian-*`, `backup-verify`, `security-secrets`, `monitoring-alerts`. Гейт в `tests/run.sh`
уже требует хотя бы одну строку доказательства у проектных отчётов.

## 2. P1 — сделано (батч 2026-09-17, коммит в тот же день)

### 2.1. Журнал проекта: агент помнит, что уже делал ✅ внедрено
**FACT:** `memory/projects/` хранит статические факты (путь, ветка, язык, риски), но не события.
**Предложение:** `agents/checks/lib/journal.sh` → `journal_write <slug> <kind> <текст>` дописывает строку в
`memory/projects/<slug>/JOURNAL.md` (kind: decision / incident / action / change). Обработчики `project-check`,
`act`, `project-run` пишут туда итог, а `proj-<slug> status` печатает последние 5 строк секцией «📌 ЧТО БЫЛО».
**Проверка:** выполнить действие, увидеть его в следующем отчёте; гейт: журнал проекта не растёт от
read-only прогонов (запись только при изменении).
**Ценность:** ответы вида «почему вчера трогали liza» перестают требовать grep по журналам.

### 2.2. Универсальный обработчик `lookup <имя>` ✅ внедрено
**FACT:** `routing.py` различает объект только если в вопросе есть слово «контейнер/процесс/сервис».
«Что там с octopus-multisync» (без слова «сервис») уезжает в общий отчёт.
**Предложение:** `agents/checks/lookup.sh` — один вход, который ищет имя сразу во всех реестрах
(юнит systemd → контейнер → процесс → репозиторий проекта → порт → путь) и печатает найденное с
доказательствами; в `routing.py` — правило-фоллбэк: если в вопросе есть известное имя и не сработало
ничего другого, идти в `lookup`. Обработчик выдаётся всем агентам через `wire-agents.sh`,
чтобы не править 27 YAML руками.
**Проверка:** «что там с octopus-multisync» → карточка именно этого юнита, а не отчёт по узлу.

### 2.3. Действия по ролям, с подтверждением и проверкой результата ✅ внедрено
**FACT:** `act.sh` умеет перезапуск/старт по allowlist юнитов; после действия проверяет `is-active`
(это уже «доказательство результата»).
**Предложение:** добавить безопасные глаголы, каждый — с ограничением по типу объекта и записью в историю:
`logs-rotate <юнит>`, `backup-now`, `clean-old-logs <дни>`, `prune-images` (уже есть), `restart` — для контейнеров
через `docker restart` с allowlist проектов. Для необратимых — обязательное подтверждение от владельца
(сообщение «делаю X на Y, подтвердите») и запись `actor=telegram:<chat_id>`.
**Проверка:** гейт «глагол без allowlist не выполняется»; история содержит запись с кодом возврата.

### 2.4. Телеметрия моделей: кто отвечает и сколько это стоит ✅ внедрено
**FACT:** `config/models.yaml` и `agents/models.py::policy_status` есть, а метрик по моделям — нет:
не видно, какой тир/модель реально обслуживает запросы и как часто срывается на дорогой резерв.
**Предложение:** писать в историю прогонов `model`, `tier`, `fallback_used`, `latency_ms`, `cost_hint`
(из ответа шлюза) и отдать метриками `hermes_model_requests_total{tier,model}`,
`hermes_model_fallbacks_total`. Правило: рост доли дорогого тира > X% за сутки → предупреждение
(«бесплатные тиры перестали отвечать»).
**Проверка:** сутки работы → в Grafana видно распределение по тирам, всплеск фолбэков объясним.

## 3. P2 — сделано в том же батче

### 3.1. Инвентаризация скиллов и права ✅ внедрено
**FACT:** в `/opt/hermes/skills` — 12 `SKILL.md`, в `/root/agents` — **248**. Реестр (`REGISTRY.md`) знает
первые. Дубликаты и «безлимитные» описания никем не проверяются.
**Предложение:** `scripts/audit-skills.sh` — инвентарь, поиск дублей по заголовку и по телу, проверка, что
у каждого скилла объявлены capability и границы (какие обработчики он имеет право вызывать); вывод — таблица
«скилл → capability → разрешённые глаголы → дубли». Ничего не удалять, только показать: 248 скиллов — это чья-то
работа, решение по ним ваше.

### 3.2. Второе мнение (verifier) для необратимых действий ✅ внедрено
**OBSERVATION:** сейчас результат действия проверяет тот же агент, который его выполнил.
**Предложение:** `agents/checks/verify-action.sh` — читает состояние объекта до/после (по истории) и
подтверждает или опровергает результат; при расхождении владельцу уходит «действие не подтверждено».
Дёшево, потому что состояние «до» уже пишется в историю.

### 3.3. Очередь и приоритеты ✅ внедрено
**FACT:** `MAX_CONCURRENT = 2` в runtime, очередь не различает приоритеты.
**Предложение:** три очереди — алерты (сразу) / запрос владельца (сразу) / фоновые и прогоны проектов
(по одному), плюс сообщение владельцу «задача N в очереди, ожидание ≈ M мин», если ждёт больше двух минут.
Это же снижает шанс, что тяжёлый проектный прогон задержит ответ на простой вопрос.

### 3.4. Суточный дайджест 09:00 ✅ внедрено
Из истории прогонов + алертов + состояния проектов: «за сутки: N прогонов, M ошибок, что изменилось в
проектах, что требуют вашего решения». Не поток токенов, а 10 строк.

## 4. Осознанно отклонено

| Идея | Почему нет |
|---|---|
| Полный произвольный shell для агента из Telegram | Токен бота и телефон — слабее SSH-ключа. Заменено управляемыми глаголами `act.sh`: фиксированные действия над проверенными именами. Расширять список глаголов — да; открывать `bash -c` из чата — нет |
| Mesh прямых связей между всеми агентами | Есть общий Agent Bus/оркестратор; N² связей ломает наблюдаемость и права |
| Второй Prometheus/свой alertmanager | Уже есть octopus-monitoring с живыми правилами; дублирование стеков противоречит «не дублировать» |
