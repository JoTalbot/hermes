# 2026-09-16 — `hermes gateway restart --system` pointed the gateway at another user's venv

## FACT
Running `hermes gateway restart --system` (recommended by `hermes gateway status` as
"installed service definition is outdated") regenerated `/etc/systemd/system/hermes-gateway.service`
with:

    ExecStart=/home/ubuntu/hermes-venv/bin/python -m hermes_cli.main gateway run

## Measured failure
    hermes-gateway.service: Failed to execute /home/ubuntu/hermes-venv/bin/python: Permission denied
    Main process exited, code=exited, status=203/EXEC   (restart counter 19)
    systemctl is-active hermes-gateway → activating (auto-restart)

The service user is `hermes`; `/home/ubuntu/hermes-venv` is another operator's environment
(and is on the do-not-touch list). The dispatcher was DOWN — a reboot would have come up
without any task dispatch.

## Fix
`deploy/systemd/hermes-gateway.service.d/10-hermes-home.conf` pins ExecStart, HERMES_HOME,
VIRTUAL_ENV, PATH and the EnvironmentFile. Drop-ins are not regenerated by that command, so
the pin always wins. `scripts/install.sh` installs it. Doctor gate 17 fails when the
EFFECTIVE unit (read via `systemctl show`, not `systemctl cat`) points outside /home/hermes.

## LESSON
"Update the service definition" is a write operation against a shared box, and the tool's
defaults were derived from whoever ran it. Treat a self-updating unit as a change to be
verified, not a fix to be trusted: check the EFFECTIVE config, and pin what must not drift.
